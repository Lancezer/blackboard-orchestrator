# 架构与技术实现

## 组成

系统由 Codex MCP、DSH 本地 bundle、控制器和文件黑板组成。Codex 使用已有本机 app-server daemon 的线程；DSH bundle 在 Web Host 注册工具和本地桥接。两端原生界面负责呈现各自会话。

`skills/to-dsh` 与 `skills/to-codex` 提供用户显式入口和模型指引。MCP 或 DSH 工具将请求写入本地临时文件，再通知控制器登记一次交接。控制器不包含规划、执行、审查或返回等固定业务路线。

```text
Codex TUI ── MCP ──┐                         ┌── DSH bundle ── DSH WebUI
                    ├── 本地控制器与控制文件 ─┤
                    └── 任务 HANDOFF 和交接文档 ┘
```

## 任务与交接

新任务分配 ID，记录参与会话、角色、工作区、涉及项目、批准情况和文档引用。一次交接包含源会话、目标端、可选目标会话 ID、目标目录及模型等选项。没有显式目标时，优先选择工作区匹配的已有参与会话，否则新建。Codex 使用 daemon 线程 ID，DSH 使用 Host 会话 ID。

登记前检查权限声明及必要的 Git 干净度，原子写入交接文档和状态。源工具立即返回；DSH 工具请求结束当前回合，Codex 工具提示模型结束。控制器等待源端空闲、输入队列清空且已知后台任务停稳，再次检查 Git 状态，等待目标空闲后发起下一回合。

目标回合可以再次调用交接工具，传入相同任务 ID；控制器在当前回合结束后处理新请求。如果没有后续请求，记录可观察到的结果并结束任务，不自动唤醒其他会话。等待和轮询只消耗本机进程资源。

## 持久化与迁移

运行目录默认是 `~/.local/share/blackboard-orchestrator/`，包括 IPC 请求、任务路径索引、日志和服务状态。单项目交接材料位于项目的 `.codex-dsh/tasks/<ID>/`，多项目材料位于运行目录下的 `tasks/<ID>/`。Git 项目身份按共同 Git 目录识别，同仓库的 worktree 属于同一项目。

`HANDOFF.md` 的元数据与正文、各次 `instruction-*.md`、结果文件均通过临时文件写入、同步和重命名持久化。多项目扩展在源会话停稳后移动目录、更新索引并保留旧路径符号链接；跨文件系统等无法安全移动的情况阻断，避免产生两份可写材料。

安装把专用目录加入用户 Git 忽略文件。各组件使用同一个默认运行目录；显式覆盖 `BLACKBOARD_DATA` 时各进程需保持一致。

## 会话设置与权限

Codex 通过 app-server `model/list` 和 `permissionProfile/list` 查询选项，并通过 `thread/settings/update` 调整已有线程的权限预设；更改从下一回合生效。同一线程的自动接续仍是用户要求的工作，不代表自动转交其他 Agent。回合模型选项通过 `turn/start` 提供。

DSH 桥接通过 session controller 的模型目录及 `permissionPresets` 服务查询和调整。预设同时影响其沙箱与审批策略，具体可选值由运行中的 DSH 决定；会话的沙箱根目录仍由创建时的 Session Header 决定。临时权限和 DSH 模型记录原值；任务结束时仅在当前值仍是本工具所设值时尝试恢复，避免覆盖用户中途手动修改。

## 生命周期与边界

适配器按需启动常驻控制器；控制器复用已有 DSH Host，或启动独立 Host 并保存本机认证地址用于打开页面和按需启用 bundle。Host 作为独立进程存活，控制器停止时不关闭它。Codex daemon 和已有用户会话不由控制器关闭。

同一控制器以任务 ID 串行交接，针对两端活动回合应用可配置并发上限。工作区独占是协作式约束，不阻止用户或其他程序绕过工具直接写文件。检查到忙碌、崩溃、超时或权限问题时记录 `BLOCKED`；重启后不自动重放未知动作。暂停、检查和人工恢复通过 CLI 完成。

原生模型调用会将必要上下文发送给各自服务；本地文件和无业务正文的控制通知不改变这一事实。订阅费用、模型可用性、平台权限和外部资源冲突由相应原生环境决定。
